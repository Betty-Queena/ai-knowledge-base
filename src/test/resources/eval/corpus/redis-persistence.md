# Redis 持久化：RDB 与 AOF

Redis 是内存数据库，一旦进程退出，内存里的数据就没了，因此它提供了两种持久化方式：
RDB 快照和 AOF 追加日志。两者可以单独使用，也可以同时开启。

## RDB：某一时刻的全量快照

RDB 把某一时刻的内存数据整体写成一个紧凑的二进制文件。触发方式有两种：
`SAVE` 会阻塞主线程直到写完，`BGSAVE` 则 fork 出一个子进程去写，主线程继续处理命令。
fork 之后父子进程共享内存页，真正发生写入时才复制被修改的那一页，
这项技术叫写时复制（Copy-on-Write），所以 fork 瞬间的内存开销并不等于数据总量，
但写入越频繁，被复制的页就越多，内存峰值也越高。

RDB 的优点是文件紧凑、恢复速度快，适合做备份和全量迁移；
缺点是两次快照之间的数据会丢失，如果两次快照之间宕机，那段时间的写入就找不回来了。

## AOF：把写命令追加到日志

AOF 把每一条写命令追加到文件末尾，恢复时重新执行一遍。
它的落盘时机由 `appendfsync` 决定：

- `always`：每条命令都 fsync，最安全，性能最差；
- `everysec`：每秒 fsync 一次，是默认值，最多丢一秒的数据；
- `no`：交给操作系统决定何时落盘，性能最好，丢失量不可控。

AOF 文件会随着时间不断变大，所以 Redis 提供了重写机制：
`BGREWRITEAOF` 会 fork 一个子进程，根据当前内存里的数据反向生成一份最小的命令集合，
用新文件替换旧文件，重写期间新的写命令会同时追加到缓冲区里，最后再合并进去。

## 混合持久化

Redis 4.0 之后支持混合持久化，配置项是 `aof-use-rdb-preamble`。
开启后 AOF 文件的前半部分是一份 RDB 格式的全量快照，后半部分是增量命令。
这样既能获得接近 RDB 的恢复速度，又能保留 AOF 只丢少量数据的特性。
如果对数据安全性要求较高，通常的做法是 RDB 与 AOF 同时开启：
用 RDB 做定期备份，用 AOF 保证重启后的数据完整性。

## 内存满了怎么办

当内存使用达到 `maxmemory` 上限时，Redis 会按照 `maxmemory-policy` 决定淘汰策略。
常见的取值有 `noeviction`（不淘汰，写入直接报错）、`allkeys-lru`（在所有键里按最近最少使用淘汰）、
`volatile-lru`（只在设置了过期时间的键里淘汰）等。
需要注意的是，如果策略选了 `volatile-*` 而大部分键又没有设置过期时间，
内存依然可能被写满，此时表现和 `noeviction` 一样。
