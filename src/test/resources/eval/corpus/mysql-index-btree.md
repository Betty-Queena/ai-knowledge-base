# MySQL 索引与 B+ 树

## 为什么是 B+ 树

InnoDB 的索引结构是 B+ 树。相比二叉树，B+ 树的每个节点能放很多个键，
树高通常只有三层左右，一次查询只需要两到三次磁盘 IO；
相比 B 树，B+ 树只在叶子节点存数据，非叶子节点只存键，
同样大小的页能放下更多键，树更"矮胖"；
而且叶子节点之间用双向链表串起来，做范围查询时顺着链表扫描即可，
不必反复回到上层节点。这三点正是它被选作索引结构的原因。

## 聚簇索引与二级索引

InnoDB 的表本身就是一棵按主键组织的 B+ 树，称为聚簇索引，
叶子节点直接存放整行数据。所以按主键查询是最快的。

二级索引（也叫辅助索引）的叶子节点存放的不是整行，而是索引列的值加上主键值。
通过二级索引查到主键之后，还要再回到聚簇索引里取整行，这一步叫**回表**。
如果查询需要的列恰好都在索引里，就不必回表，这种索引称为覆盖索引，
在 `EXPLAIN` 的 Extra 列里会显示 `Using index`。

## 最左前缀原则

联合索引 `(a, b, c)` 是按 a、再按 b、再按 c 的顺序排序的，
所以它能被用上的条件是查询条件从最左边开始连续匹配：

- `WHERE a = ?`、`WHERE a = ? AND b = ?`、`WHERE a = ? AND b = ? AND c = ?` 都能用上；
- `WHERE b = ?` 或 `WHERE b = ? AND c = ?` 用不上这个索引；
- `WHERE a = ? AND c = ?` 只能用到 a 这一列，c 用不上（在 MySQL 8.0 的索引条件下推下可以在引擎层过滤，但仍不能用于定位）。

另外，范围查询会截断后续列：`WHERE a = ? AND b > ? AND c = ?` 中 c 用不到索引定位。

## 索引失效的常见写法

- 对索引列使用函数或表达式，例如 `WHERE YEAR(created_at) = 2024`、`WHERE id + 1 = 5`；
- 隐式类型转换，例如字符串列 `phone` 与数字比较 `WHERE phone = 13800000000`；
- 以通配符开头的模糊匹配 `LIKE '%关键字'`，因为无法利用有序性；
- `OR` 两侧并非都有索引，可能导致整体退化成全表扫描。

## 怎么确认索引有没有用上

用 `EXPLAIN` 看几个关键列：`type` 反映访问方式，
从优到劣大致是 `const`、`eq_ref`、`ref`、`range`、`index`、`ALL`，
出现 `ALL` 说明走了全表扫描；`key` 是实际选择的索引；
`rows` 是预估扫描行数；`Extra` 里出现的 `Using filesort` 表示需要额外排序，
`Using temporary` 表示用到了临时表，这两项都值得警惕。

索引不是越多越好：每个索引都要在写入时维护，占用空间，也会拖慢插入和更新。
选择性地给区分度高的列建索引，比给每一列都建一个要划算得多。
对于很长的字符串列，还可以只索引前若干字符，也就是前缀索引。
