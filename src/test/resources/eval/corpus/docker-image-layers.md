# Docker 镜像分层与构建缓存

## 镜像是一叠只读层

Dockerfile 里的每一条指令（`RUN`、`COPY`、`ADD` 等）都会生成一个层，
镜像就是这些只读层叠加起来的结果。容器启动时并不修改镜像本身，
而是在所有只读层之上再加一个可写层，所有写操作都落在这个可写层里，
删除容器时它也就一起消失了。读文件时从最上面的层往下找，找到就返回，
这个机制叫写时复制（Copy-on-Write）。

分层带来的直接好处是复用：如果两个镜像的前几层完全相同，
宿主机上只会保存一份，拉取和推送时也只需要传输缺失的层。

## 构建缓存怎么命中

构建镜像时，Docker 会逐条指令判断能否复用上一次的缓存：
只要指令本身没变，且它依赖的上一层缓存还在，这一层就直接复用，不必重新执行。
问题在于 `COPY` 和 `ADD`：只要被复制文件的内容有任何变化，
这一层的缓存就失效，并且它后面所有层的缓存也跟着失效。

所以 Java 项目常见的写法是先把依赖描述文件单独复制进去、下载依赖，最后才复制源码：

```
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests
```

这样日常改动源码时，只有后面两层需要重建，下载依赖那一层仍然命中缓存，
构建时间会明显缩短。反过来，如果写成 `COPY . .` 再 `RUN mvn package`，
任何一次源码改动都会导致依赖重新下载。

## 多阶段构建

编译型语言的项目通常需要 JDK、Maven 等只在构建期用得到的工具，
如果直接把它们留在最终镜像里，体积会大很多。
多阶段构建允许在一个 Dockerfile 里写多个 `FROM`，
构建阶段可以给一个名字，后续阶段用 `COPY --from=` 把产物拷过来，
最终镜像只包含运行期真正需要的部分。

## .dockerignore

`docker build` 会把构建上下文整个发给守护进程。
如果上下文里包含 `.git`、`target`、`node_modules` 这类目录，
传输会很慢，而且可能意外破坏缓存。把这些路径写进 `.dockerignore` 可以避免。

## tag 与 digest 的区别

tag 是可以被覆盖的，同一个 `latest` 今天和下周可能指向完全不同的镜像内容；
digest 是镜像内容的哈希值，只要内容不变它就不变。
因此在需要严格复现的环境里，用 `image@sha256:...` 这种形式引用镜像，
比依赖 tag 更可靠。
