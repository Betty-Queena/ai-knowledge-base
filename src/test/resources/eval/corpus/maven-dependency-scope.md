# Maven 依赖范围与传递依赖

## scope 决定了依赖在哪些阶段可见

`<scope>` 控制一个依赖在编译、测试、运行三个阶段是否出现在类路径上，也决定它会不会被传递给下游。

- `compile`：默认值，三个阶段的类路径上都有，会传递给依赖本项目的其他项目；
- `provided`：编译和测试时可见，运行时由容器或 JDK 提供，打包时不进产物，也不传递。
  典型例子是 `servlet-api`；
- `runtime`：编译时不可见，测试和运行时可见，会传递。典型例子是 JDBC 驱动，
  代码里只用到 `java.sql` 接口，运行时才需要具体实现；
- `test`：只在测试的编译与执行时可见，不传递，也不进产物。JUnit、Mockito 属于这一类；
- `system`：需要显式写出本地路径，不推荐使用，可移植性差。

## 依赖冲突时谁赢

传递依赖让依赖树可能变得很深，同一个坐标出现多个版本时，Maven 的调解规则是"路径最短优先"：
离本项目越近的版本胜出。如果两个版本到根的距离相同，则先声明的那一个胜出。

这里有个容易被忽略的后果：把某个依赖直接写进 `pom.xml`，
它的"距离"就变成了 1，于是它自然而然压过所有传递进来的版本。
这也意味着升级一个直接依赖，可能会顺带改变一串间接依赖的版本。

## 控制传递的几种手段

- `<optional>true</optional>`：声明这个依赖是可选的。
  它对本项目完全正常，但不会传递给下游项目，下游需要就自己声明。
- `<exclusions>`：把某个传递依赖排除掉。引入一个重量级组件时，
  常常需要顺手排除它自带的老版本日志实现，避免和项目里的日志门面打架。
- `<dependencyManagement>`：只统一版本号，本身并不引入依赖。
  子模块声明依赖时不写版本，就会取这里管理的版本，从而保证多模块版本一致。
- `import` 范围的 BOM：`spring-boot-dependencies` 这类 BOM 通过
  `<scope>import</scope>` 导入，效果是把一大片依赖的版本统一托管，写法比逐个声明简洁得多。

排查冲突最直接的命令是 `mvn dependency:tree`，
加上 `-Dincludes=groupId:artifactId` 可以把整棵树裁剪到只关心的那一枝。
`mvn dependency:analyze` 则能找出"声明了但没用到"和"用到了但没声明"的依赖。
