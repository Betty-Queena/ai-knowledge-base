# JWT 认证机制与常见误区

## 结构：三段 Base64URL

一个 JWT 由三部分组成，用点号连接：头部（header）、载荷（payload）、签名（signature）。
头部描述签名算法和类型；载荷放具体的声明（claim）；
签名是把前两段拼起来、用密钥按指定算法算出来的结果。

关键的一点是：前两段只是 Base64URL 编码，不是加密。
任何人都能把载荷解出来读，所以**不要把密码、身份证号这类敏感信息放进载荷**。
签名保证的是"内容没被篡改"，而不是"内容不可见"。

## 常用声明

载荷里的声明分三类：注册声明、公共声明和私有声明。
注册声明是预定义好的一批字段，常用的有：

- `sub`：主体，一般是用户标识；
- `exp`：过期时间，服务端必须校验；
- `iat`：签发时间；
- `nbf`：在此时间之前不可用；
- `iss`：签发者；
- `aud`：接收方。

自定义业务字段（比如角色、租户号）属于私有声明，注意别和注册声明重名。

## 为什么它适合做无状态认证

传统的 Session 方案下，服务端要保存每个会话的状态，
多实例部署时要么做会话粘滞，要么把 Session 存到 Redis 里共享。
JWT 把状态放在令牌自身，服务端只需要用密钥验签就能确认身份，
天然适合横向扩容，这也是它在前后端分离和微服务场景里流行的原因。

## 代价：撤销很麻烦

令牌一旦签发，在过期之前始终有效，服务端没有"踢人下线"的天然手段。
常见的缓解办法有三种：把有效期设得很短，配合 refresh token 定期换新；
维护一份黑名单，登出时把未过期的令牌记进去，每次校验都查一下
（这等于又引入了状态，需要权衡）；或者给用户维护一个令牌版本号，
改密码或强制下线时把版本号加一，旧令牌自然失效。

## 几个必须避开的坑

- **不校验算法**：如果服务端只解码不验签，或者允许客户端指定算法，
  攻击者可以把头部改成 `alg: none`，或者用公钥当 HMAC 密钥来伪造签名。
  正确做法是服务端固定允许的算法，不接受客户端传来的算法。
- **不校验 exp / iss / aud**：签名有效不等于令牌可用，这几个字段都要校验。
- **密钥硬编码在代码或配置文件里提交进仓库**：密钥泄露等于任何人都能签发合法令牌。
- **放在 localStorage 里**：容易被 XSS 读取；放在 HttpOnly Cookie 里能防 XSS，
  但会引入 CSRF 问题，需要配合 SameSite 或 CSRF Token 使用。
  两种存法各有取舍，不存在无脑最优解。
