# JVM 垃圾回收基础

## 堆为什么要分代

绝大多数对象的生命周期都很短，少数对象会活很久，
把这两类对象放在一起管理，回收效率会很低。
所以堆内存被划成新生代和老年代：新对象优先在新生代的 Eden 区分配，
Eden 满了就触发一次 Minor GC，把还活着的对象挪到 Survivor 区，
在 Survivor 之间来回搬运若干次之后仍然存活的对象，才晋升到老年代。
老年代满了会触发 Major GC 或 Full GC，停顿时间通常明显更长。

## 怎么判断对象还活着

主流 JVM 不用引用计数，而是用可达性分析：
从一组称为 GC Roots 的对象出发（栈上的局部变量、静态变量、常量引用、JNI 引用等）
做遍历，遍历不到的对象的就可以回收。

Java 里的引用分成四档，影响的就是"还有没有可能在遍历中被保住"：
强引用是最普通的引用，只要还在就绝不回收；
软引用在内存不足时才回收，适合做缓存；
弱引用在下一次 GC 时就会被回收；
虚引用只用来在对象被回收时收到一个通知。

## 常用的回收器

- Serial：单线程回收，至今仍是客户端模式下的默认选择，简单、内存占用小；
- Parallel：多线程回收，关注吞吐量，适合批处理任务；
- CMS：以低停顿为目标的老年代回收器，标记清除算法会产生内存碎片，新版本已不再推荐；
- G1：把堆划分成大小相等的 Region，可以是新生代也可以老年代，
  按"回收收益"排序，优先回收垃圾最多的那些 Region，
  通过 `-XX:MaxGCPauseMillis` 设定期望的停顿目标，JVM 会据此挑选本次回收的 Region 数量。
  单个对象超过 Region 一半大小会被当成 Humongous 对象特殊处理。
- ZGC：以极低停顿为目标，停顿时间基本与堆大小无关，代价是更高的内存占用。

## 几个常用参数

`-Xms` 与 `-Xmx` 分别是最小和最大堆，生产上一般设成相同值，
避免运行期反复扩容缩容；`-Xmn` 指定新生代大小；
`-XX:MetaspaceSize` 影响元空间首次触发回收的阈值（JDK 8 以后永久代已被元空间取代）。

排查内存问题时，最值得先加的是 `-XX:+HeapDumpOnOutOfMemoryError`，
它能在抛出 OutOfMemoryError 的瞬间把堆转储下来，
配合 `-XX:HeapDumpPath` 指定存放位置，事后再用 MAT 之类的工具分析。
GC 日志则能回答"到底是谁把老年代撑满了"这类问题：
开启方式在不同 JDK 版本里写法不同，JDK 9 以后统一用 `-Xlog:gc*`。
